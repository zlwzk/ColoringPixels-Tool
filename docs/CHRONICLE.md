## 第一章 · 起因：不想再一格一格点下去

《Coloring Pixels》本质上是「按数字填色」。一张图小则几百格，大则几千格，重复劳动占了绝大部分。
最初的动机非常朴素：**能不能让当前这一关直接涂完？**

有两条路：

1. 直接改存档字段，把进度写成「已完成」；
2. 找到游戏自己的填色逻辑，模拟一次真实的填色过程。

第一条路五分钟就能写完，但很快被否掉了——那样进度条不会动、统计不增长、成就也不会解锁，
本质上只是把存档改脏了。最后选了第二条：定位 `CrossLevelStorage` 与 `ClickTest`，
用游戏自身的判定去填，**让工具产出的结果和手涂完全一致**。

插件跑起来之后立刻遇到第二个问题：受众根本没听过 BepInEx，更不知道 `winhttp.dll` 该丢在哪。
于是顺手写了安装器：自动找目录、部署运行时、启动游戏，一步到位。
这个"顺手"后来变成了项目里代码量最大的部分之一。

## 第二章 · 从「涂完」到「涂得像人」

一键涂完的第一个反馈是：**太假了**。几百格在一帧里全部出现，进度条瞬间拉满，完全不像人在玩。

于是有了「拟人涂色」：按颜色逐个处理，就近分块 + 蛇形扫行 + 随机停顿 + 手速抖动，
甚至加入「偶尔点错一格再回头补上」。目标只有一个——看起来像一个人坐在那里慢慢涂。

也是在这一版意识到：**不是所有人都想跳过游戏**。
有一类用户只想自己涂，但嫌一格一格点太累。于是做了「画布颜色高亮」：
把当前选中颜色对应的待涂格子高亮出来，方便肉眼快速定位。
这就是后来「人工辅助」模块的第一颗种子。

## 第三章 · 更名：它已经不只是一个 Cheat

1.2.0 做了一次改名：`ColoringPixelsCheat` → `Coloring Pixels Tool`。

理由很直接——它已经变成「安装器 + 插件 + 文档 + 发布流程」的一整套东西，
叫 Cheat 会让人以为只有一个 DLL。改名时特意保留了插件 GUID `coloringpixels.cheatsuite`，
这样老用户的配置文件、背景图、等级数据都不会丢。

同一版本里把「提交 → 推送 → 打标签 → 等 CI → 把安装器放到桌面」串成了一条命令。
**每次发版要比写代码轻松，这件事本身很重要**，否则发版会一年只做一次。

## 第四章 · 当工具开始有自己的界面

1.3.0 是界面上的分水岭：面板从「一页塞满」变成 8 个标签
（首页 / 涂色 / 拟人 / 自动化 / 辅助 / 解锁 / 设置 / 调试），并加入计时器、
自动化总时长、快捷键可视化绑定。

随后 1.3.1 做了一件一开始以为很简单的事：**汉化游戏本体设置界面**。
结果游戏的像素字体不认中文，全部显示成方块，只好连字体一起换掉；
同时把词典做成可外挂的文件，保存后热重载，方便随时补充。

同一版本安装器学会了「检查更新」——用户不用再自己盯着 Releases 页面。

## 第五章 · 2.0.0：把工具做「重」

2.0.0 塞进了几个看起来很"不务正业"的功能：等级系统、称号、自定义面板背景。

等级系统的真实目的不是激励，而是**给长时间挂机一个叙事外壳**：
屏幕上有一条经验条在涨，比冷冰冰的「剩余 37 分钟」要好看得多。
也是在这一版，经验增长被大幅放缓，并把「手动点击率」纳入判定——
挂机收益明显低于真人操作，避免工具把游戏彻底变成放置类。

这一版还修掉了一个非常隐蔽的 bug：
安装器判断「已是最新」时只比较文件长度。负载重建之后，新旧文件长度**恰好相同**，
于是插件永远更新不上，用户看到的却是「成功」。改成逐字节比对之后问题消失。
教训是：**"看起来成功了"比"失败"更危险。**

## 第六章 · 2.1.0：第二个游戏，以及一次被迫的抽象

《涂色大师：像素梦想家》是 IL2CPP 构建，注入托管插件这条路走不通。

与其硬啃，不如换个思路：**不改内存、不注入，用屏幕扫描 + 模拟鼠标**。
于是有了独立助手 `PixelAssist.exe`：框选画布、逐行扫过、全屏点击穿透的 HUD 指示进度。

这次绕路反而促成了项目里最重要的一次重构：
把扫描引擎抽成与游戏无关的 `Assist*` 核心，
插件（Coloring Pixels 的「人工辅助」模块）和独立助手**共用同一套实现**。
一个原本只为绕开技术障碍的妥协，最后变成了架构上最干净的一层。

同一版本，面板按职责分成「自动完成 / 人工辅助」两大模块，并加入自适应缩放——
低分辨率下文字互相覆盖的问题，终于被 `GUI.matrix` 一次性解决。

## 第七章 · 2.2.0：好看也是一种功能

这一版花了不少时间在「动效」上，起因是研究了 magicui 与 Aceternity UI 的设计语言。

难点在于**不能引入任何前端依赖**：插件跑在 Unity 的 IMGUI 上，
安装器与助手跑在 .NET Framework 4.0 的 WinForms 上。
于是 Shimmer、Glare、ShineBorder、Spotlight、Aurora、Dot Grid、Grain、
Border Beam、Pulse、彩纸……全部手写。

一个意外的收获是三端统一：插件面板、安装器、独立助手现在用同一套
「深靛蓝 + 青紫霓虹 + 玻璃卡片」的视觉语言。用户在三处看到的是一致的质感，
而不是三个风格迥异的工具。

## 第八章 · 护栏：防手滑比功能本身更重要

项目里最容易被忽视、但现在看来最有价值的一块，是各种「确认」。

- **爱心二次确认**：游戏里点一次爱心 = 清空全部进度并回到第 1 关，不可撤销。
  插件在游戏自己的确认框之后再拦一道，并给确认键加 2 秒冷静期。
- **自动绘图上锁**：「涂色 / 拟人 / 自动化」三页会写存档，默认上锁。
  第一次解锁会弹出风险说明，确认键有 3 秒冷静期；确认之后长期有效，
  之后启动游戏不再询问，也可以在设置里重新上锁。

结论是：一个"作弊工具"最重要的设计，其实是**让你不容易后悔**。

## 一路上的取舍

| 取舍点 | 最终选择 | 原因 |
| --- | --- | --- |
| 改存档 vs 模拟游戏逻辑 | 模拟游戏逻辑 | 进度、统计、成就仍由游戏自己计算，结果与手涂一致 |
| 引入 UI 库 vs 手写绘制 | 全部手写 | 插件是 Mono + IMGUI，安装器是 .NET Framework 4.0，没有可用的现成方案 |
| 单个安装包 vs 每款游戏一个 | 一个 | 用户只需要下载一次；两款游戏各自记忆目录与状态，互不影响 |
| 默认开放自动绘图 vs 默认上锁 | 默认上锁 | 一进游戏就手滑涂完整张图，是最难挽回的操作 |
| 只做功能 vs 也做视觉 | 两者都做 | 工具会被长时间盯着看，界面质感直接影响使用意愿 |
